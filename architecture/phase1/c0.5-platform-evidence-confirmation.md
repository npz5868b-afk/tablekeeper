## Proposed shared interface

The following is the W2 proposal for exact agreement with Reservation Core. Commands shown are the stable container entrypoints; image names are always resolved to immutable digests by the lock before execution.

### Migration invocation and readiness orchestration

Migration:

```text
docker compose --project-name tablekeeper-c2 --file platform/compose.c2.yaml run --rm --no-deps migration /app/bin/reservation-core migrate --database-url-env TK_DATABASE_URL --migrations /app/db/migrations --expected-contract-sha256 70167f82812a4ccef11b76f4d358b90374aa34dc38d977c5bff487315d1ea3ec --output /evidence/staging/migration.json
```

Orchestration is fail-closed and ordered: verify locks and frozen hashes; create internal networks and volumes; start PostgreSQL 17 by digest; wait for `pg_isready`; run the one-shot core-owned migration entrypoint; require exit `0` and a machine-readable migration record; run the core-owned migration compatibility/readiness check; start Reservation Core; require its readiness document; only then enable proof execution. A timeout, hash mismatch, dirty/unknown image reference, missing migration record, schema-version mismatch, or nonzero command prevents dependent services from starting.

Readiness outputs are JSON documents with platform fields `component`, `status` (`READY` or `NOT_READY`), `checkedAt`, `buildId`, `contractGraphSha256`, and `checks[]` (`name`, `status`, `reasonCode`, `observedFact`). Reservation Core owns the meaning and implementation of its `database`, `migrations`, and `domain` checks; W2 only gates on their status and records the bytes and digest.

### Seed-fixture contract

W2 will not author domain seed facts. Reservation Core supplies an immutable fixture file plus a core-owned loader. The W2 handoff descriptor is:

```json
{
  "fixtureContractVersion": "1.0.0",
  "fixtureId": "<stable-id>",
  "fixturePath": "/fixtures/c2/<file>",
  "fixtureSha256": "<64 lowercase hex>",
  "randomSeed": "<decimal string>",
  "clockInstant": "<RFC3339 UTC>",
  "loaderBuildId": "<Reservation Core build id>"
}
```

Invocation:

```text
/app/bin/reservation-core seed --descriptor /fixtures/c2/seed-descriptor.json --output /evidence/staging/seed-result.json
```

The loader must be deterministic, tenant-explicit, idempotent for the same descriptor, reject a digest mismatch, and return a result containing `fixtureId`, `fixtureSha256`, `loaderBuildId`, `startedAt`, `finishedAt`, `result`, and `observedCounts`. W2 treats domain payload and counts as opaque evidence and never performs reservation-table DML.

### Proof-hook invocation

```text
/app/bin/reservation-core prove --suite c1-reservation-db --seed-descriptor /fixtures/c2/seed-descriptor.json --execution-id <uuid> --build-id <build-id> --output /evidence/staging/core-proof
```

The hook returns nonzero on any failed assertion and writes immutable candidates: `test-executions.json`, `artifacts.json`, and raw outputs. Each test execution maps exactly to frozen `TestExecutionEvidence`: `testId`, `testDefinitionDigest`, `executionId`, `startedAt`, `finishedAt`, `environmentDigest`, `result`, `artifactPaths`, with optional `observedFact` and `interpretation`. W2 adds no domain assertions; it verifies structure, recomputes digests, and packages outputs.

### Audit/event and attempt ingestion fields

Logs do not become a second audit authority.

### Pinned/offline runtime boundary

- PostgreSQL is major-version pinned to 17 and image-pinned by immutable digest; all other runnable images are also digest-pinned.
- Dependency restoration/build is a separate preparation phase using lockfiles. The evidence run uses `--pull never`, performs no package installation, and fails when a pinned image or dependency cache is absent.
- Runtime networks are Docker `internal` networks. Reservation Core reaches PostgreSQL only; proof drivers reach only the declared service endpoint; generators/verifiers that need no service access use `--network none`. No default bridge is used.
- Internet denial is tested from every execution container and recorded as frozen `NetworkControlEvidence` with the control artifact digest.
- Deterministic inputs are the fixture digest, declared random seed, frozen clock instant where time-dependent behavior is under test, build ID, contract graph digest, image digests, and test-definition digests.
- Cloud services, hosted models, remote indexes, telemetry exporters, and alternate state stores are absent from the correctness path.

## Reservation mutation exclusion proof

The topology and privilege proof is a set of enforceable negative capabilities:

1. Only the Reservation Core runtime receives the PostgreSQL `core_runtime` credential. Its network route is limited to PostgreSQL, and all reservation commands enter its deterministic domain command handler.
2. `core_runtime` is the only runtime role granted reservation-state DML. Reservation Core owns the grant SQL, constraints, RLS policies, and transaction boundaries. C2 verifies grants and default privileges but does not author domain privileges.
3. The one-shot `migration` role exists only during migration, is not exposed to the running service or proof drivers, and cannot be used as an application credential.
4. Seed execution is a core-owned loader invoked before proofs. Platform mounts an immutable descriptor and receives a result; it has no SQL client path or reservation DML credential.
5. Evidence collection receives only structured stdout/files and a read-only audit export surface. It has no PostgreSQL credential and no network route to PostgreSQL.
6. Failure injection controls containers, signals, and networks only. It cannot issue domain commands or SQL.
7. Readiness and health endpoints are query-only and run under no database role capable of mutation.
8. Negative C2 checks inspect container secrets, routes, PostgreSQL role memberships/grants/default privileges, and attempt direct DML from every non-core component; any successful write fails the run.
9. Transaction rollback, process interruption, ambiguous-response retry, and dependent-service outage proofs compare authoritative pre/post state and require audit/outbox atomicity. Platform records results; only the core hook evaluates reservation semantics.

Therefore every non-core platform component is excluded by both credential and network capability from reservation mutation. The only admitted mutation path is `generated command envelope -> Reservation Core adapter -> deterministic domain service -> PostgreSQL transaction`, with PostgreSQL constraints deciding commit success. This is the C0.5 design proof; executable negative-capability evidence is a required C2 deliverable, not claimed complete here.
