## Proposed W1 ↔ W2 interface

### Migration entrypoint

Command surface:

```text
reservation-core/bin/migrate.ps1 -DatabaseUrl <postgres-url> -Mode <up|verify|down> [-Target <migration-id>]
```

Contract:

- PostgreSQL 17 only; fail closed on another major version.
- `up` takes a PostgreSQL advisory migration lock, applies ordered immutable SQL files once, and records file SHA-256 plus migration ID in `reservation_core.schema_migrations`.
- `verify` performs no schema mutation and rejects missing, reordered, or digest-mismatched migrations.
- `down` is permitted only where the migration declares a tested reverse step; destructive production rollback is not implied.
- Exit `0` on success, nonzero on version, readiness, lock, digest, SQL, or verification failure; stdout emits one structured JSON result and stderr contains diagnostics without secrets.

Initial migration boundary: extensions/schema and separated roles; tenant/venue/service-period/resource/group/policy tables; preparation/reservation/allocation/accepted-terms/idempotency tables; audit/outbox/attempt tables; constraints, indexes, triggers, RLS policies, and grants. No application/runtime composition is included.

### Readiness dependencies

W1 requires only:

- a reachable PostgreSQL 17 server;
- a migration owner credential for migration commands, unavailable to request handling;
- a non-owner, non-`BYPASSRLS` application credential for domain proofs;
- transaction-local tenant context support via `SET LOCAL`/`set_config(..., true)`;
- required PostgreSQL extensions declared by the first migration and verified before use;
- the frozen W0 files above mounted/readable for conformance and digest verification.

Database liveness alone is insufficient. W1 readiness is true only after PostgreSQL major-version, migration-digest, required-extension, application-role/RLS, and tenant-context reset checks pass. W2 may orchestrate these checks but may not redefine them or bypass failure.

### Seed-fixture interface

Command surface:

```text
reservation-core/bin/seed.ps1 -DatabaseUrl <postgres-url> -Fixture <absolute-json-path> -Seed <uint64> -Mode <apply|verify>
```

The JSON input is schema-versioned and deterministic: `fixtureVersion`, `seed`, tenants, venues, service periods, atomic resources, versioned groups, immutable policy versions/terms, and optional initial preparations/reservations. Stable fixture keys are mapped deterministically to IDs; timestamps must be explicit UTC values. `apply` runs in one transaction and is idempotent for the same fixture digest. `verify` is read-only. The command emits fixture digest, seed, migration head, row counts by entity, and outcome. It never silently truncates or resets data.

### Proof-hook command surface

One dispatcher is exposed to W2:

```text
reservation-core/bin/prove.ps1 -DatabaseUrl <postgres-url> -Suite <all|migration|allocation|group-atomicity|idempotency|versioning|rollback|rls|pooled-context|audit-outbox> -Seed <uint64> -OutputDirectory <absolute-path> -ExecutionId <id> -BuildId <id>
```

It returns nonzero if any assertion fails and writes deterministic JSON plus TAP/JUnit-compatible detail. The surface includes contention winner cardinality, complete group allocation, prepare/confirm separation, consumed-token replay, idempotency replay/mismatch, stale-version rejection, atomic modify/cancel, transaction rollback, audit/outbox co-commit, cross-tenant denial, and pooled-context reset. W2 owns runtime setup, failure injection, network controls, and evidence packaging; W1 owns the assertions and reservation semantics.

### Structured audit/event outputs

Authoritative outputs are PostgreSQL rows, not logs:

- transactional outbox: one logical committed business event per successful logical mutation, in the same transaction as domain state;
- immutable domain audit record: tenant, actor, command, correlation, idempotency digest, aggregate ID/type, expected/result version, event type, outcome, occurred time, contract version, and build ID;
- append-only command-attempt record: accepted/rejected/rolled-back/unknown-response outcome with request fingerprint and safe error code, written in the governing transaction or a separate post-rollback/rejection transaction as allowed by C11.

Payloads serialize using the W0 C11 generated/schema definitions. Raw idempotency keys, tokens, credentials, and unredacted guest secrets are forbidden. Observability exports are non-authoritative copies.

## Mutation-boundary proof

The implementation boundary will enforce the following call graph:

```text
generated contract input
  -> thin adapter (validation/mapping only; no SQL)
  -> deterministic command service
  -> PostgreSQL transaction runner
  -> repositories using only the supplied transaction handle
  -> domain rows + audit + outbox commit together
```

Enforcement mechanisms:

1. Query services receive a read-only transaction capability and cannot call mutation repositories.
2. Mutation repositories are not exported outside the W1 domain package and cannot create connections or commit independently.
3. Every state-changing service requires a transaction handle created by the single command transaction runner; direct pool access is forbidden by package boundaries and a static import-boundary test.
4. The runner sets and verifies tenant context transaction-locally before any repository call; application connections use a non-owner, forced-RLS role.
5. PostgreSQL constraints remain final authority: exclusion constraints protect atomic occupied ranges; foreign/unique/check constraints and RLS protect identities, versions, tenancy, and legal persistence.
6. Domain mutation, version advancement, allocation changes, accepted terms, audit, idempotency finalization, and outbox insertion occur in one transaction. Rollback proofs assert zero partial effects.
7. Seed and migration tools are separate administrative entrypoints and credentials; they are unavailable to request/runtime adapters and are not reservation mutation APIs.
8. A repository/import scan and database proof suite will fail C1 if any alternate write path, non-transactional mutation, owner-role request path, or alternate state store exists.

Therefore no UI, model, retrieval process, runtime orchestrator, proof packager, adapter, or query path can mutate reservation truth; all authorized reservation changes converge on deterministic domain services and PostgreSQL transactions.
