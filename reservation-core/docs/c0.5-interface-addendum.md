## One executable contract

Reservation Core owns one platform-neutral CLI application named `reservation-core`. Its argument grammar and JSON outputs are identical on every host. Packaging may expose it as:

- `/app/bin/reservation-core` in the pinned OCI image used by W2;
- `reservation-core/bin/reservation-core.cmd` on Windows; or
- `reservation-core/bin/reservation-core` on POSIX.

Those launchers contain no semantics; each invokes the same locked Reservation Core CLI build. W2 invokes `/app/bin/reservation-core` in the image and must not reproduce migration, seed, readiness, or proof logic in platform scripts. Secrets are passed by environment-variable **name**, never as argument values.

Global behavior for every subcommand:

- stdout is exactly one UTF-8 JSON result document; diagnostics go to stderr with secrets redacted;
- exit `0` means the requested operation and all required checks passed; any failure is nonzero;
- unknown flags, unknown document versions, digest mismatches, PostgreSQL other than major 17, and missing required inputs fail closed;
- all output paths are absolute container/host paths supplied by the caller;
- W1 owns the JSON document schemas under `reservation-core/contracts/cli/v1/**`; these are operational interface schemas, not substitutes for C01–C12 wire types. Frozen values embedded in them use generated/schema-derived C01–C12 types.

### Migration

```text
/app/bin/reservation-core migrate \
  --mode <up|verify|down> \
  --database-url-env <environment-variable-name> \
  --migrations <absolute-directory> \
  --expected-contract-graph-sha256 <64-lowercase-hex> \
  [--target <migration-id>] \
  --output <absolute-json-path>
```

`up` uses the migration role, advisory-locks the migration ledger, and applies immutable ordered files. `verify` is read-only and checks PostgreSQL version, extensions, order, IDs, and recorded file digests. `down` is accepted only for a migration with an explicit tested reverse operation. The result document is `migration-result/v1` and includes `operation`, `result`, PostgreSQL major version, migration head, applied IDs/digests, contract-graph digest, start/finish instants, and safe failure code.

### Seed

```text
/app/bin/reservation-core seed \
  --database-url-env <environment-variable-name> \
  --descriptor <absolute-json-path> \
  --mode <apply|verify> \
  --output <absolute-json-path>
```

The descriptor is the only fixture argument and has this exact `seed-descriptor/v1` shape:

```json
{
  "descriptorVersion": "1.0.0",
  "fixtureId": "<stable-id>",
  "fixturePath": "<absolute-json-path>",
  "fixtureSha256": "<64 lowercase hex>",
  "randomSeed": "<unsigned decimal string>",
  "clockInstant": "<RFC3339 UTC>",
  "loaderBuildId": "<Reservation Core build id>"
}
```

The descriptor does not restate domain fixture content. W1 owns the immutable fixture and loader semantics. The loader verifies the fixture digest, applies under the `core_runtime` role through the same deterministic transaction/repository boundary used by domain commands, is tenant-explicit and idempotent for the descriptor digest, never truncates/reset tables, and emits `seed-result/v1`: descriptor/fixture identity and digest, loader build, migration head, seed, clock, start/finish instants, result, safe failure code, and observed counts.

### Readiness

```text
/app/bin/reservation-core readiness \
  --database-url-env <environment-variable-name> \
  --expected-contract-graph-sha256 <64-lowercase-hex> \
  --output <absolute-json-path>
```

This is the sole authoritative W1 readiness invocation. It is read-only and uses `core_runtime`. The exact `readiness-result/v1` document is:

```json
{
  "documentVersion": "1.0.0",
  "component": "reservation-core",
  "status": "READY",
  "checkedAt": "<RFC3339 UTC>",
  "buildId": "<build id>",
  "contractGraphSha256": "<64 lowercase hex>",
  "migrationHead": "<migration id>",
  "checks": [
    {
      "name": "<postgresql-major|migration-digests|required-extensions|runtime-role|rls|tenant-context-reset|domain-query>",
      "status": "PASS",
      "reasonCode": "<stable code>",
      "observedFact": "<safe factual summary>"
    }
  ]
}
```

Top-level `status` is `READY` only if every required check is `PASS`; otherwise it is `NOT_READY` and the process exits nonzero. W2 orchestrates `pg_isready`, then `migrate`, then this command, and gates startup on the emitted bytes without recreating check meanings.

### Proofs

```text
/app/bin/reservation-core prove \
  --suite <c1-reservation-db|migration|allocation|group-atomicity|idempotency|versioning|rollback|rls|pooled-context|audit-outbox> \
  --database-url-env <environment-variable-name> \
  --seed-descriptor <absolute-json-path> \
  --execution-id <uuid> \
  --build-id <build-id> \
  --output-directory <absolute-directory>
```

`c1-reservation-db` is the complete aggregate suite; the remaining names select stable subsets. There is no separate `--seed` flag. The proof hook validates/applies the descriptor as required, returns nonzero if any assertion fails, and writes exactly:

```text
<output-directory>/
  result.json
  test-execution-candidates.json
  artifact-candidates.json
  junit.xml
  raw/
```

- `result.json` is `proof-result/v1` with suite, result, execution/build IDs, contract graph, migration head, descriptor digest, assertion totals, and start/finish instants.
- `test-execution-candidates.json` is `test-execution-candidates/v1`. Each operational candidate carries the test identity and definition digest, execution ID, start/finish instants, environment-digest input, result, staging-relative artifact paths, and optional observed fact/interpretation needed for deterministic projection.
- `artifact-candidates.json` is `artifact-candidates/v1`. Each operational candidate carries a staging-relative path, SHA-256, and media type for emitted proof artifacts other than the two candidate index files. It contains no `readOnlyRetained` field or final-retention claim and does not self-reference.
- `junit.xml` is a diagnostic projection; it is not authoritative evidence.
- `raw/` contains deterministic machine-readable assertion detail and redacted command diagnostics.

The two candidate files are operational handoff documents, not frozen C12 `TestExecutionEvidence` or `ArtifactEvidence` objects. W1 owns all domain assertions, test identities/results, test-definition digests, staging-relative paths, content digests, and media types. W2 copies candidate files byte-for-byte, independently verifies every declared digest, and deterministically projects them into frozen C12 objects without semantic reinterpretation.

## Evidence handoff

W2 supplies a fresh staging directory and maps it as `/evidence/staging/reservation-core`. It invokes the four commands above with outputs exactly here:

```text
/evidence/staging/reservation-core/
  migration.json
  readiness.json
  seed-result.json
  proofs/
    result.json
    test-execution-candidates.json
    artifact-candidates.json
    junit.xml
    raw/
```

W2 copies the byte-identical tree into its run's `raw/migration/`, `raw/readiness/`, `raw/seed/`, and `raw/proofs/` areas. It prefixes each staging-relative candidate path with the final run-relative `raw/proofs/` namespace, independently recomputes every digest, and creates the frozen `TestExecutionEvidence` and `ArtifactEvidence` objects. W2 also hashes and declares `test-execution-candidates.json` and `artifact-candidates.json` themselves as final `ArtifactEvidence`; neither candidate index attempts to include itself or the other index, avoiding self-reference and mutual-reference cycles. W2 enforces read-only retention first and sets `readOnlyRetained: true` only in the final frozen artifact objects after that enforcement succeeds. Projection is mechanical and schema-validating: W2 may prefix paths and add C12 packaging/retention facts, but may not change W1 test identity, definition digest, execution identity, result, observed fact, interpretation, artifact bytes, digest, or media type.

W1 writes nowhere under `platform/**`; W2 writes nowhere under `reservation-core/**`.

## Database roles and negative grants

Exactly two login roles are admitted to W1 database operations:

- `reservation_core_migration`: migration-only owner role. It owns W1 schemas/objects and may create/alter/drop them. It is absent from the running Reservation Core service, seed/proof runtime, readiness runtime, and every W2 evidence/failure-injection component.
- `core_runtime`: non-owner, non-superuser, non-`BYPASSRLS` runtime role. It receives only explicit schema usage, sequence access as required, domain table DML needed by deterministic command services/seed proofs, and query access needed by retrieval/readiness. RLS is enabled and forced on every tenant-owned table.

No other runtime role receives reservation table DML. Default `PUBLIC` schema/table/sequence/function privileges are revoked, default privileges for future W1 objects are deny-by-default, and `core_runtime` is not a member of `reservation_core_migration` or any owner/bypass role. Transaction-local tenant context is set and verified before tenant-owned access and is reset by transaction end.

The core-owned proof suite must assert at minimum:

1. `core_runtime` is not superuser, owner, `BYPASSRLS`, or a member of the migration role.
2. the migration role credential is absent from runtime/proof/readiness environments;
3. `PUBLIC` and every non-core runtime/evidence role have no reservation schema DML, sequence mutation, owner membership, or security-definer path to mutation;
4. default privileges cannot grant future reservation-object access accidentally;
5. cross-tenant reads, writes, joins, and allocation operations fail under forced RLS;
6. pooled reuse cannot retain tenant context;
7. readiness uses no mutation and W2 evidence/failure-injection components have neither database credential nor route;
8. all allowed `core_runtime` writes still traverse W1 deterministic services/repositories and an explicit PostgreSQL transaction—database grants are necessary capability, not an alternate public mutation API.

W2 may independently inspect and attempt negative access, but the grant policy and authoritative assertions remain W1-owned.

## Ownership and blockers

Paths remain disjoint. W1 ownership remains `reservation-core/**`; this addendum does not claim `architecture/**`, `platform/**`, or `contracts/w0/**`. W2 retains only its previously declared `platform/**` and Platform C0.5 artifact paths. The shared interface is invoked across the container/file boundary; neither lane edits the other's implementation.

Blockers to C0.5 PASS remain: Platform & Evidence must accept this exact interface, Contract Steward must confirm the operational descriptor/result schemas do not diverge from frozen C01–C12 types, and the Coordinator must record reconciliation and C0.5 PASS. C1A remains on hold.
